# ADR-022: npm 이름 `@tty.link/font-kku`와 공개 버전 체계

## Status
Accepted

## Date
2026-10-11

## Context
- npm 첫 공개(TODO P1)를 앞두고 이름과 버전을 정해야 했다. 둘 다 한 번 올리면 되돌리기 어렵다.
  - **이름**: npm에는 이름 바꾸기가 없다. 새 이름으로 다시 올리고 옛 이름에 `npm deprecate` 안내를 붙이는 수밖에 없다. 그러면 쓰던 사람이 모두 import와 CDN 주소를 고쳐야 한다.
  - **번호**: 한 번 쓴 버전 번호는 unpublish해도 다시 쓸 수 없다.
- 지금까지 버전은 저장소 안에서만 올렸다. 0.1.0(2026-03 MVP), 0.3.0(2026-07 TRK-030), 0.4.0(2026-10 TRK-033)이다. npm·PyPI·crates.io·RubyGems·Go proxy 어디에도 올린 적이 없고 git tag도 없다(2026-10-11 확인).
- 사용자 의견(2026-10-11): 이름은 조직 scope로 한다. 첫 공개는 0.1.0으로 하고, 0.1.0 → 0.2.0처럼 크게 뛰지 말고 0.1.0 → 0.1.1처럼 작게 올린다.
- 버전이 적힌 자리는 마흔 곳 남짓이다. 패키지 매니페스트 7곳에, 문서·사이트·AI 설명서의 jsDelivr 주소 110여 곳이 더 있다. 손으로 바꾸면 빠뜨린다.

## Decision
### 1. 이름
- npm 패키지 이름은 **`@tty.link/font-kku`**다(npm 조직 `tty.link`, 공개 패키지라 무료).
- 바뀌지 않는 이름도 있다.
  - 태그·클래스(`<font-kku>`, `class="font-kku"`)
  - 명령 `font-kku-text`
  - 다른 언어 패키지 이름(PyPI `font-kku`, crate `font-kku`, gem `font_kku`, Go 모듈 경로)
- 설치하지 않은 곳에서 명령을 쓰는 견본은 `npx -p @tty.link/font-kku font-kku-text`로 쓴다. `npx font-kku-text`는 레지스트리에서 이름이 `font-kku-text`인 다른 패키지를 찾기 때문이다.

### 2. 번호는 공개 기준으로 0.1.0에서 다시 시작한다
- 첫 공개 버전은 **0.1.0**이다. 공개된 번호가 하나도 없으니 겹치는 곳이 없다.
- 저장소 이력에 남은 0.1.0–0.4.0은 공개하지 않은 내부 번호였다. CHANGELOG에서 이 ADR 날짜 앞의 번호는 내부 번호로 읽는다.

### 3. 0.x 동안의 규칙 — 패치가 기본, 마이너는 깨질 때만
| 바꾸는 것 | 예 | 올리는 자리 |
|---|---|---|
| 기존 페이지가 그대로 도는 변경 전부 | 버그·글꼴 교정, 새 글꼴·테마·꾸밈·움직임, 새 속성·옵션·CSS 변수, 문서 | **패치** 0.1.0 → 0.1.1 |
| 기존 페이지를 깨는 변경 | 속성·CSS 변수·`part`·`data-fy-*` 이름을 빼거나 바꿈, 페이지 CSS가 어긋나게 기본 배치를 바꿈, 배포 파일을 빼거나 옮김 | ~~**마이너** 0.1.x → 0.2.0~~ → **0.1.x 동안은 이것도 패치**(2026-10-12 사용자 결정, 아래) |
| 공개 계약을 안정으로 선언 | 속성·CSS 변수·DOM 계약 동결 | 1.0.0 |

- 이 규칙은 패키지 매니저가 0.x를 다루는 방식과 같다. 모두 0.1.x 안에서는 호환으로 보고, 0.2.0은 직접 올려야 받는다.
  - npm `^0.1.0`(= `>=0.1.0 <0.2.0`)
  - Cargo `0.1`
  - RubyGems `~> 0.1.0`
  - PEP 440 `~=0.1.0`
- 그래서 패치로 낸 교정과 새 기능은 쓰는 사람이 따로 손대지 않아도 받는다.
- 글꼴 교정으로 모양이 조금 달라지는 것은 교정(패치)이다. 페이지가 의존하는 계약(이름·구조)이 바뀔 때만 마이너다.
- **보강(2026-10-12, 사용자 결정):** 0.1.x 동안은 기존 페이지 출력이 바뀌는 공개도 패치로 올린다(0.1.0 → 0.1.1). 처음 의견("크게 뛰지 말고 작게")을 따른다.
- **후보판(2026-10-15, 사용자 결정):** 공개 전 런타임 탐색(§6의 3 워크플로)을 돌리지 않고 탐침만 거친 공개는 `X.Y.Z-rc.N`으로 낸다.
  npm `next` 꼬리표(`npm publish --tag next` — `release_gate.py`가 `latest`로 올리는 후보판을 막는다)라 `npm install`·`^0.1.0`은
  정식 판에 머물고, `@X.Y.Z-rc.N`·`@next`로 밝힌 사람만 받는다. 전체 탐색을 통과하면 같은 코드(또는 고친 코드)를 정식 `X.Y.Z`(latest)로
  낸다. Python은 PEP 440 `X.Y.ZrcN`, Ruby는 `X.Y.Z.rcN`으로 적는다(`bump_version.py`). font.tty.link는 후보판으로도 배포한다 —
  "사이트는 최신 상태를 테스트 하는 곳이기도 한거야"(복사 코드도 `@X.Y.Z-rc.N`). `0.1.3-001`처럼 이미 나온 판 뒤에 꼬리를 붙이면
  semver에서 그 판보다 앞선 판이 되고(숫자 꼬리의 앞자리 0은 잘못된 판), 업데이트가 아니라 되돌림으로 보여 쓰지 않는다.
  - 대가: npm `^0.1.0`·Cargo `0.1`·RubyGems `~> 0.1.0`·PEP 440 `~=0.1.0`으로 받는 곳은 바뀐 출력을 자동으로 받는다. 문서의 CDN 주소는 정확한 판이라 직접 올릴 때만 바뀐다.
  - 그래서 그런 패치는 CHANGELOG 릴리스 줄에 바뀌는 것과 예전 출력을 지키는 법(예: `font="sebul"`, `face="device"`)을 적는다.
  - 첫 적용은 0.1.1이다(기본 배치 세벌 고정, 바탕 요소 `aria-label` 없앰, 정적 렌더러 원소 획 등). 0.2.0은 공개 계약을 안정으로 선언하기 전 큰 정리가 있을 때 다시 정한다.

### 4. 한 버전을 함께 쓴다
- npm 패키지와 Python·Rust·Ruby 렌더러는 같은 번호를 쓴다. 정본은 `package.json`의 `version`이다.
- Go 모듈은 소스에 번호가 없다. 공개 저장소의 release tag `renderers/go/v<버전>`이 번호다.
- 명세 파일 버전(`spec/tables.json` 1.3, `html-cases.json` 1.9, `test-cases.json` 1.4, `render-plan.json` 1.0 — 2026-10-12 기준)은 계약 버전이라 따로 간다.

### 5. 문서의 CDN 주소는 정확한 버전에 고정한다
- 문서는 `@tty.link/font-kku@0.1.0`처럼 정확한 번호로 쓴다. `@0.1` 같은 범위 주소는 쓰지 않는다.
- 런타임은 CSS·글꼴·확장을 스크립트 주소 기준으로 받는다. 범위 주소는 파일마다 따로 풀리고 CDN 캐시가 바뀌는 동안 런타임과 CSS가 다른 버전으로 섞일 수 있다.
- 번호를 바꿀 때는 `python3 scripts/bump_version.py <버전>`이 매니페스트 7곳과 문서 주소·tarball 이름·문서 페이지 버전 자리를 한꺼번에 바꾼다. CHANGELOG·IMPL_STATUS·TODO·ADR·리뷰 기록은 당시 기록이라 건드리지 않는다.
- `--check`는 하나라도 다르면 실패하며, `npm run verify`(빠른 묶음 포함)의 `Version copies` 단계로 돈다.

### 6. 릴리스 순서
이 절이 공개 절차의 정본이다. [TESTING.md](../../TESTING.md) 'CI와 릴리스 점검표'와 운영 노트는 이 절을 가리키고 다시 적지 않는다.
npm 공개와 사이트 배포는 사용자가 승인한다. 공개를 준비하는 에이전트는 아래 차례를 따르고, 5의 틀을 다 채우기 전에는 승인을 청하지 않는다.

1. **공개할 커밋을 만든다.** `python3 scripts/bump_version.py <버전>`을 실행한다. CHANGELOG에 `YYYY-MM-DD release <버전>` 줄을 쓴다. 이 줄에는 바뀌는 것, 예전 출력을 지키는 법, 알려진 문제, 답 없이 기본값으로 정한 결정을 적는다. 그리고 커밋한다.
   - 판 번호를 verify 뒤에 올리면 패키지 파일이 바뀌어 검증한 커밋과 공개할 커밋이 갈린다. 그래서 번호를 먼저 올린다.
   - 3의 탐색 워크플로를 돌리지 않을 공개는 후보판 번호(`X.Y.Z-rc.N`, §3 후보판)로 올린다.
2. **그 커밋에서 `npm run verify:release`를 돌린다**(공개 층 — 전체 측정 표본, 캐시를 읽지 않음). 트리가 깨끗해야 한다. summary JSON이 git HEAD, 트리 더러움, pack 무결성을 함께 적어 이 커밋에 묶인다.
   - 공개 층 단계 'Release review sheets'가 직전 공개판(npm에 올라간 바이트) 대비 전후 시트를 만들고 summary `reviewSheets`에 경로를 적는다. 모양은 판정하지 않는다. 시트는 5의 ②에서 사용자가 본다.
3. **공개 전 탐색 점검을 돌린다.** `tests/probes/run.py`로 재현 탐침을 다시 돌린다([사용법](../../tests/probes/README.md)). 직전 공개판 이후 런타임 영역(`font-kku*.js`·`font-kku*.css`·`profiles/`)이 바뀌었으면 탐색 점검 워크플로도 돌린다. 범위는 직전 공개판부터의 diff로 좁힌다. 절차는 [runtime-sweep.md](../NOTES/runtime-sweep.md).
   - 보고 전용 도구(헷갈리는 짝 `scripts/glyph_confusable_audit.py`, 재료 × 꾸밈 `tests/matrix_probe.py`)는 판정하지 않는다. 2의 `verify:release`가 맨 끝 보고만 단계(`Confusable pairs audit`·`Matrix probe`)로 돌고 summary `reports`에 남긴다. 시트를 열어 본다.
   - 실패한 탐침(고쳤던 결함이 돌아옴)은 심각도와 상관없이, 이번 판에서 새로 생긴 높음 회귀는 고친 뒤 2부터 다시 한다. 아직 안 고친 알려진 결함의 탐침은 `KNOWN`을 달아 실패해도 막지 않는다(보고만). 오래된 결함은 TODO_LIST '공개판 알려진 문제'에 적고 공개를 막지 않는다.
   - 다른 무거운 작업과 동시에 돌리지 않는다(AGENTS.md §병렬 작업).
   - **배포 미리보기 정적 사이트 점검**: 사이트 저장소의 `scripts/site_preview_check.py`가 공개할 라이브러리의 후보 tarball로 사이트를 정적으로 빌드하고 127.0.0.1에서 내준다. 모든 쪽을 세 엔진·데스크톱·휴대폰으로 열며, tty.link는 공개 사이트를 열되 `font.tty.link/lib/**`만 후보 사본으로 돌린다. 공개 사이트와 견줘 오류·실패 요청·예외가 있거나 덜 그려진 바탕 요소가 늘면 실패다. 전후 시트는 5의 ②에서 함께 보인다. 사이트 패키지 의존 버전과 복사 코드 주소는 사이트의 `scripts/update_package.py`로 공개할 버전에 맞춘다(ADR-029). **공개 전에 한 번만 돈다** — 8의 배포 전에 다시 돌지 않고 공개와 배포 사이의 변경도 검증하지 않는다(사용자 결정 2026-10-15).
4. **`scripts/release_gate.py`가 승인 보고를 찍는다.** package.json `prepublishOnly`에 걸려 있어 `npm run prepublishOnly`로 먼저 돌려 본다. summary와 HEAD를 대조하고 승인 보고(그 사이 바뀐 패키지 파일 등)를 찍는다. `npm publish`도 같은 검사를 다시 돌려 조건이 깨졌으면 멈춘다.
5. **사용자가 승인한다.** 아래 '공개 승인 요청 틀'을 채워 보인다. 승인 링크(npm 2FA)는 사용자가 틀을 보고 준비됐다고 할 때만 띄운다.
6. **`npm publish`.** 2FA가 필요하므로 maintainer가 승인한다. 자동 배포를 붙이면 trusted publishing이나 `npm stage publish`를 쓴다.
   - 후보판은 `npm publish --tag next`(관문이 꼬리표를 본다).
   - 웹 2FA 승인 링크는 약 5분 뒤 만료된다. 브라우저에서 npmjs.com에 먼저 로그인해 둔다.
   - 대화형 터미널에서 실행한다. 비대화형 셸에서는 승인을 기다리지 않고 가려진 링크만 찍고 끝난다.
   - 메인 checkout(`.git`이 디렉터리)에서 실행한다. npm은 `<git 루트>/.git/HEAD`를 읽어 `gitHead`를 적으므로 worktree나 풀어 놓은 tarball에서 공개하면 빠진다(0.1.4-rc.2). `release_gate.py`가 막는다.
   - 올린 뒤 registry·jsDelivr에 보이기까지 몇 분 걸린다. `npm view @tty.link/font-kku version`으로 확인한다.
   - 공개한 커밋은 `npm view @tty.link/font-kku@<버전> gitHead`로 안다(npm이 공개할 때 HEAD를 적는다). 로컬 git tag는 사용자가 청할 때만 만든다.
7. **`scripts/check_cdn_min.py`.** jsDelivr에 새 버전이 보이면 압축본 길(`font-kku.min.js`가 받는 `.min` CSS·확장·자소 모듈)이 원본과 DOM·화소까지 같게 그리는지 본다(2026-10-12 Change Log).
8. **font.tty.link를 배포한다**(사용자 승인). 사이트 저장소의 `scripts/build.py`로 소스와 패키지에서 `dist/`를 만들고 생성물 전용 배포 checkout에 동기화한다(ADR-029). `--published-tarball <별도로 받은 npm 공개본> --require-published`로 런타임·CSS·글꼴·선택 모듈의 추가·변경·삭제를 공개된 같은 버전과 대조한다. 사이트의 복사 코드는 jsDelivr의 정확한 `@<버전>` 주소를 유지한다. 배포 전에 3의 미리보기를 다시 돌지 않는다. 후보 tarball만 쓰는 빌드는 개발 미리보기이며 공개본과 같다고 취급하지 않는다. 소스 checkout을 배포 출력 대상으로 사용하지 않으며, Pages 브랜치 전환·push는 별도 승인 후 수행한다.
   - **문서만 고칠 때는 공개하지 않는다**(2026-10-13 사용자 결정). 설명서·README(.md), 명세 .json, 타입 .d.ts는 사이트 쪽이 npm보다 새로워도 빌드가 알리기만 하고 배포한다. AI 설명서 주소는 판 없는 `https://font.tty.link/lib/skill/SKILL.md`(늘 최신)이고, 설명서 안의 코드 주소는 공개된 판에 고정돼 있어 받는 코드와 어긋나지 않는다. npm·jsDelivr의 문서 사본은 다음 코드 공개 때 함께 바뀐다. 사이트 문서는 공개된 동작만 설명한다(런타임 파일 대조가 지킨다).

공개 저장소가 생긴 뒤에는 `scripts/export_public.py v<버전> --push`로 tag를 붙이고, Go tag `renderers/go/v<버전>`도 만든다(사용자 승인).

#### 공개 승인 요청 틀
승인을 청할 때 여섯 칸을 모두 채운다. 해당이 없으면 '없음'이라고 적는다. 한 칸이라도 비어 있으면 승인 링크를 청하지 않는다.

- **① 커밋** — 검증한 커밋(summary)과 공개할 커밋, 그 사이 패키지 파일 차이(`release_gate.py` 출력). 같으면 '같음'.
- **② 전후 시트** — 직전 공개판 대비 시트(summary `reviewSheets`)의 경로나 그림을 사용자에게 직접 보인다. 16·24·32·48·120px 문단과 헷갈리는 짝을 담는다. 에이전트·LLM 판정단이 본 것으로 대신하지 않는다.

## Alternatives Considered
### 비스코프 이름 `font-kku`
- 짧고, 이미 문서 주소가 이 이름이었다.
- 하지만 만든 곳이 이름에 드러나지 않는다. 패키지를 나눌 때(입력기·렌더러 등) 묶을 자리도 없다. 문서 주소를 바꾸는 일은 한 번이면 끝나니 걸림돌이 아니었다.

### 0.4.0 그대로 공개
- 문서 주소를 바꿀 필요가 없었다.
- 하지만 공개 이력은 처음부터 시작하는데 번호만 중간에서 시작하게 된다. 내부 번호를 이어 갈 이유도 없었다.

### 0.x에서도 새 기능은 마이너
- SemVer 1.0 이후의 관례(기능 = 마이너)를 0.x에 적용하면 기능을 더할 때마다 0.2.0, 0.3.0으로 뛴다.
- 그러면 `^0.1.0`으로 설치한 사람은 아무것도 받지 못한다. 사용자가 원한 작은 걸음과도 맞지 않는다.

## Consequences
- 보통의 릴리스는 0.1.1, 0.1.2…로 간다. 0.1.x 동안은 출력이 바뀌는 공개도 패치다(2026-10-12 보강). 그때는 CHANGELOG에 무엇이 바뀌었고 예전 출력을 어떻게 지키는지 적는다.
- 릴리스마다 문서 주소 110여 곳이 바뀐다. 스크립트가 바꾸고 검사가 지키지만, diff는 커진다.
- `package.json`에서 아직 없는 공개 저장소를 가리키던 `repository`·`bugs`를 뺐고 `homepage`는 `https://font.tty.link/`다. 공개 저장소가 생기면 다시 넣는다.
