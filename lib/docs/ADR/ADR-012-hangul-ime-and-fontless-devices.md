# ADR-012: 한글 입력기 모듈과 한글 글꼴 없는 기기 지원

## Status
Accepted

## Date
2026-10-10

## Context
한글 입력기(OS IME)도 한글 글꼴도 없는 기기가 있다. 키오스크, 최소 설치 리눅스, 외국에서 빌린 컴퓨터, 일부 TV·전자책 브라우저다. 이런 기기에서 웹 페이지가 한글을 보이고 받으려면 두 가지가 모두 필요하다.

- **보이기**: 폰꾸의 그림 자소(`sprite`) 재료는 자소판 그림으로 자소를 그려 기기 글꼴이 필요 없다(ADR-008 §5). 그런데 코어 그림 자소 규칙은 자소 노드만 칠했다. 한글 음절이 아닌 글자로 분류되는 **낱자**(`ㅋㅋ`, 입력 중인 `ㄱ`, 호환 자모 U+3131~)는 `[part="content"]`로 기기 글꼴이 그려 두부(네모)가 됐다. 입력 중에는 거의 모든 음절이 한 번은 낱자 상태를 거친다.
- **입력**: 영문 자판의 키를 두벌식·세벌식 배열로 받아 음절을 조합해야 한다. 브라우저에는 그런 기능이 없다.
- 페이지가 기기 글꼴 재료 글꼴(`sebul` 등)을 쓰다가 글꼴 없는 기기에서만 그림 자소 글꼴로 바꾸려면, 기기가 한글을 그릴 수 있는지 알아야 한다.

사용자 요청(2026-10-10): 이런 기기에서 영문 자판으로 두벌식·세벌식 한글을 쳐서 쓰는 전광판·메모장을 데모에 넣고, 필요하면 이 환경을 고려해 설계를 개선한다.

## Decision

### 1. 입력기는 선택 모듈 `font-kku-ime.js`로 패키지에 싣는다
- 루트 `font-kku-ime.js`(classic/CommonJS) + `font-kku-ime.mjs`(같은 객체를 다시 내보내는 ESM) + 형식 `font-kku-ime.d.ts`·`.d.mts`. npm에서는 `font-kku/ime`, 브라우저에서는 `window.FontKkuIme`. 폰꾸 런타임과 의존 관계가 없다 — 조합 결과는 보통 문자열이다.
- 순수 층: `createComposer(layout)`(키 하나씩 → `{ commit, composing }`), `convert(keys, layout)`(`"\b"`는 Backspace), `lookup`·`keyMap`(화면 자판용 표), `keyFromEvent`. DOM 층: `attach(field, options)`이 `<input>`·`<textarea>`의 `keydown`을 가로채 조합 구간을 필드 값에 직접 쓴다(`setRangeText`). 필드 값이 진짜 유니코드라 복사·붙여 넣기·폼 제출·스크린리더가 그대로 동작한다.
  - → 2026-10-13 보강(되돌리기): 초점이 있는 칸에는 `document.execCommand("insertText" | "delete")`로 쓴다(조합 구간을 선택한 뒤 바꿔 쓴다). 브라우저 되돌리기 기록에 남아 Cmd/Ctrl+Z·Shift+Z가 듣는다. 세 엔진 실측에서 `setRangeText`는 기록을 남기지 않을 뿐 아니라 그때까지의 기록을 지웠다. 그래서 `setRangeText`는 초점이 없거나(화면 키보드) 명령이 듣지 않을 때만 쓴다. 되돌리기 단위는 엔진 몫이다. Chromium·Firefox는 키 하나씩(안녕 → 안녀 → 안ㄴ …), WebKit은 이어 친 글을 한 번에 되돌린다. 페이지가 받는 `input` 이벤트는 키 하나에 한 번이다(명령이면 브라우저의 진짜 이벤트에 `fontKkuIme` 표시를 단다). WebKit이 명령에 내는 `beforeinput`은 다시 조합하지 않는다.
  - → 2026-10-13 보강(칸 종류): 선택이 없는 `<input>`(`email`·`number`·`date` …, `selectionStart`가 `null`)은 조합 구간을 바꿔 쓸 수 없다. 그래서 `attach()`가 `TypeError`로 거절한다. 전에는 붙고 나서 키마다 `setRangeText` 예외가 났고 친 글(숫자까지)이 사라졌다. 붙인 뒤 `type`이 그런 값으로 바뀌면 키를 가로채지 않고 브라우저에 넘긴다(경고 한 번).
- 배열: 두벌식 표준(KS X 5002), 세벌식 390, 세벌식 최종(3-91). 키 → 자모 표는 libhangul `hangulkeyboard.h`와 같은 값이고(사실 정보라 값만 옮김), 테스트가 네 행 × Shift 유무 전부를 골든 문자열로 고정한다. 문장 단위 기대값은 표에서 역산하지 않고 손으로 친 키 순서다.
- 조합 규칙: 합자 모음 7종, 겹받침 11종, 두벌식 받침 넘김(갑+ㅏ → 가바, 값+ㅏ → 갑사), 두벌식은 같은 자음 두 번이 된소리가 아님(Shift로만), 세벌식은 넘김 없이 같은 초성 두 번 → 된소리·같은 종성 ㄱㄱ/ㅅㅅ → ㄲ/ㅆ. Backspace는 음절을 만든 입력의 역순으로 자모 하나씩 지운다(입력 목록을 하나 빼고 다시 조합).
- 키는 물리 자리(`KeyboardEvent.code`)로 읽어 Caps Lock·OS 자판 배열(AZERTY 등)에 흔들리지 않는다. 숫자판 키는 배열과 무관하게 둔다. 한/영 전환은 Shift+Space와 한/영 키(`HangulMode`/`Lang1`), OS 입력기가 조합 중인 키(`isComposing`)는 건드리지 않는다. 초점 없는 칸에 화면 키보드로 넣을 때는 입력기가 마지막 캐럿을 기억한다(Chrome이 초점 없는 칸의 선택을 문서 선택에 끌려 처음으로 돌리는 경우가 있다).

### 2. 그림 자소 바탕 요소는 낱자도 자소판으로 칠한다
- 렌더할 때 바탕 요소의 재료가 `sprite`면, 한 코드 포인트짜리 비한글 글자가 자소판 표(자음 19·모음 21·겹받침 11)에 있는 자모일 때 그 `[part="content"]` 노드에 자소 노드와 같은 `data-sprite-jamo`·`data-sprite-jamo-kind`·`data-sprite-jamo-index`·`--fy-sprite-jamo-index`를 찍는다. 코어 그림 자소 규칙이 그대로 칠하고, 코어는 그 칸을 글자 상자 위쪽의 블록으로(곁 여백 없이) 둔다.
- 칸은 자소 노드와 같은 행 규칙을 받는다(글꼴의 `[data-sprite-jamo-kind]` 행 규칙). 자소판 칸은 음절 안 자리에 맞춰 그린 것이라, 낱자는 그 자리의 모양(예: ㄱ은 왼쪽 위)으로 보인다. 페이지는 `--fy-content-*`로 옮길 수 있다.
- **기기 글꼴 재료에서는 찍지 않는다.** 사이드카가 그리는 `sebul`·`gothic`의 DOM(`spec/html-cases.json`)은 그대로다. 재료가 바뀌면 구조가 바뀐 것으로 보고 다시 그린다(기존 `sameStructure` 비교).
- 자모 깊이는 바꾸지 않는다. 페이지가 그림 자소 글꼴에 `syllable` 깊이를 걸면 완성형 머리 노드는 자소판 칸이 없어 기기 글꼴로 돌아간다 — 이미 문서화된 동작(`image-sprite-fonts.md`)이고, 글꼴 없는 기기용 화면은 깊이를 바꾸지 않는다고 문서에 적는다.

### 3. `FontKku.hasHangulFont(options?)` — 기기 글꼴 확인
- 캔버스 `measureText`의 글자 상자(폭·actualBoundingBox 네 값)로 `가`와 미할당 `U+D7A4`, `ᄀ`(U+1100)과 미할당 `U+0378`을 비교한다. 없는 글자는 같은 두부·`.notdef` 상자(Firefox는 같은 크기의 16진 상자)로 그려지므로 같으면 `false`. 기기 글꼴 재료는 첫가끝 자모를 그리므로 두 묶음을 모두 본다.
- 픽셀을 읽지 않는다(지문 수집 방지 기능의 잡음·권한 창을 피한다). 스스로 돌지 않고 부를 때만, font-family 문자열별로 캐시한다. 판단할 수 없으면(DOM·캔버스·actualBoundingBox 없음) `null`.
- 자동 글꼴 교체는 런타임에 넣지 않는다. 페이지가 결과를 보고 `font` 속성을 바꾼다(문서에 예시). 웹 앱은 결과가 `false`이거나 `?hangul-font=none`이면 화면 글을 영어로, 기기 글꼴 재료 제목을 그림 자소 글꼴로 바꾼다.

### 4. 웹 앱 두 개를 사례에 둔다
- 사이트 `src/sign.html`(전광판)·사이트 `src/memo.html`(메모장), 공용 부품 사이트 `src/app-kit.js`·사이트 `src/apps.css`. 사례 페이지의 "웹 앱" 구획에서 잇고 메뉴는 다섯 그대로다(두 앱은 사례를 현재 메뉴로 밝힌다).
- 메모장은 `<textarea>`를 보이지 않는 입력 칸으로만 쓰고(키·접근성), 보이는 면은 줄마다 폰꾸 바탕 요소로 그린다. 캐럿·조합 중인 음절·선택 영역은 텍스트 모델과 그려진 글자 노드를 같은 순서로 맞춰 겹쳐 그린다. 위·아래·Home·End는 그려진 줄 기준으로 옮긴다.
- 검증은 글꼴을 지우지 않고 구조로 한다: 글꼴 없는 모드에서 화면에 칠해지는 한글 텍스트 노드가 모두 그림 자소 노드(투명 글자 + 자소판 배경, 그림자 없음)인지 브라우저 스모크가 훑는다.

## Alternatives Considered
### 입력기를 사이트 스크립트로만 두기
- 설명: `site/` 안에 데모 전용 스크립트로 둔다.
- 장점: 패키지 표면이 늘지 않는다.
- 단점: 키오스크·사내 도구처럼 같은 환경에서 폰꾸를 쓰는 사람이 가져다 쓸 수 없다. 조합기는 DOM 없는 순수 함수라 패키지에 싣는 비용(파일 4개, 형식, 스모크)이 작다.

### 런타임 안에 입력기를 넣기
- 설명: `FontKku.ime`처럼 런타임에 합친다.
- 장점: 파일 하나.
- 단점: 그리기와 무관한 코드가 모든 페이지에 실린다. 입력기는 폰꾸 없이도 쓸모가 있다(글꼴이 있는 기기의 입력기 없는 키오스크).

### 낱자를 한글 글자(`kind: "hangul"`)로 분류해 자소 노드 하나로 그리기
- 설명: 호환 자모를 음절처럼 분해해 자소 노드를 만든다.
- 장점: 자리 변수(`--fy-<slot>-*`)를 그대로 받는다.
- 단점: 텍스트 모델·`html-cases`·사이드카 네 언어의 분류 계약이 모두 바뀐다. 재료가 그림 자소일 때만 표면을 찍는 쪽이 같은 결과를 계약 변경 없이 낸다.

### 그림 자소 글꼴에서 `syllable` 깊이를 `whole`로 강제
- 설명: 머리 노드가 생기지 않게 깊이를 바꾼다.
- 장점: 기기 글꼴로 돌아가는 노드가 없다.
- 단점: 페이지가 고른 깊이를 런타임이 몰래 바꾸고, 문서화된 폴백 계약과 테스트를 뒤집는다. 글꼴 없는 화면이 깊이를 건드리지 않으면 되는 문제다.

### 픽셀 비교로 글꼴 확인
- 설명: 두 글자를 캔버스에 그려 픽셀을 비교한다.
- 장점: 더 많은 경우를 구분한다.
- 단점: 지문 수집 방지(캔버스 잡음·권한 창)에 걸리고, Firefox 16진 상자는 글자마다 픽셀이 달라 오판한다. 글자 상자 비교는 두 문제가 없다.

## Consequences
### Positive
- 한글 글꼴·입력기가 없는 기기에서도 영문 자판만으로 한글을 쓰고 읽는 화면을 폰꾸로 만들 수 있다.
- 그림 자소 글꼴의 "기기 글꼴 없이 같은 모양" 약속이 낱자까지 지켜진다.
- 입력기는 폰꾸 없이도 쓸 수 있는 의존성 없는 모듈이다.

### Negative
- 패키지 파일이 4개 늘고 형식 표면(`FontKkuIme`)을 유지해야 한다.
- 낱자 칸은 음절 안 자리 모양이라 일반 글꼴의 가운데 정렬된 호환 자모와 다르게 보인다.

### Risks
- 안드로이드 기기 키보드는 영문 모드에서도 `keydown`에 키를 주지 않고(`keyCode 229`) 조합 이벤트로 보내는 경우가 있어 가로챌 수 없다. 웹 앱은 화면 자판을 제공하고, 터치 기기에서 화면 자판을 켜면 입력 칸을 `inputmode="none"`으로 둔다.
- `hasHangulFont()`는 휴리스틱이다. 지문 수집 방지가 글자 상자 값까지 흔들면 `true`(글꼴 있음)로 기울어 기기 글꼴 재료를 그대로 쓴다. 웹 앱은 `?hangul-font=none`으로 강제할 수 있다.
- 그림 자소 자소판이 PNG에서 SVG로 바뀌어도 칸·행 계약은 같아 이 결정에 영향이 없다. 큰 전광판 크기(240px 이상, 전체 화면)의 자소판 해상도는 SVG 전환 뒤 다시 본다.
